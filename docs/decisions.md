# Decisions

Why the project is built the way it is. Add an entry when you make a trade-off, and don't reverse one without asking the owner.

|---|---|---|---|
| 2026-11-16 | **Everything on free tiers** (no SMS, payment gateway, maps, Play Store fee, domain) | Dev stage; the goal is a live client demo at ₹0 | The client signs off |
| 2026-11-16 | **Monorepo** (npm workspaces): `apps/web`, `apps/api`, `apps/mobile`, `packages/shared` | One API serves web and app; types are defined once | — |
| 2026-11-16 | **API on Cloudflare Workers + Hono + D1** | Free, never sleeps (free Render-style hosts take 30–50 s to wake, which ruins a live demo), TypeScript shares types with web | Traffic outgrows the D1 free limits |
| 2026-11-16 | **Website as a static export served by a Worker** (`apps/web/wrangler.jsonc`), not Cloudflare Pages | Wrangler 4.16x routes new Pages projects through Workers; static-asset Workers are the supported, free path | SSR or middleware is needed |
| 2026-11-16 | **Vercel disconnected** | Its builds broke after the monorepo move, and Cloudflare is the single host. Don't add `vercel.json`. | — |
| 2026-11-16 | **Mobile app in Flutter** (not a Capacitor wrapper) | Owner's choice: a native app for the client | — |
| 2026-11-16 | **Phone + OTP login with a fixed demo OTP (`1234`)** | No SMS cost; the website shows the hint via `NEXT_PUBLIC_DEMO_OTP` | Add an SMS provider after sign-off |
| 2026-11-16 | **Sessions are random bearer tokens; only a SHA-256 hash is stored**, 30-day expiry | Simple, works for web and app alike, and a DB leak doesn't expose usable tokens | — |

| 2026-11-16 | **Wallet is real inside QuikFly**: debit on booking, refund on cancel, in one D1 batch with a ledger row | The client noticed the wallet wasn't charged; money must never drift | A payment gateway is added |
| 2026-11-16 | **Rides are completed by the website** (`POST /bookings/:id/complete`) when the simulated trip ends | No driver app yet | The driver app exists |
| 2026-11-16 | **Account deletion: soft delete with a 30-day grace period** (sign-in restores the account; afterwards it is erased on the next sign-in) | Google Play requires in-app deletion; Uber's pattern | — |
| 2026-11-16 | ~~**Licence check for self-drive is simulated**~~ (superseded below by manual review): "pending" became "verified" after 20 s | Shows the Zoomcar-style KYC flow without a paid KYC service | A KYC provider is chosen |
| 2026-11-16 | **Invoices are printable pages** (browser "Save as PDF"), not server-made PDFs | Free, no PDF library in the Worker | Real GST invoicing is needed |

| 2026-11-16 | **Admin panel is a separate static app** (`apps/admin`, its own Worker), not a section of the website | Admin code never ships to customers; the address can be put behind Cloudflare Access (free ≤ 50 users) | — |
| 2026-11-16 | **Admins sign in with email + password** (PBKDF2 via Web Crypto, lockout after 5 failures), not the customer OTP | The demo OTP is public, so phone login can't protect staff tools; no email or SMS cost | Cloudflare Access or SSO |
| 2026-11-16 | **Fixed roles with a permission map in `@quikfly/shared`** (`owner`, `operations`, `content`); every admin write gets an `audit_log` row | API and admin UI use one source of truth; staff can move money and change prices, so changes must be traceable | More granular roles are needed |
| 2026-11-16 | **Catalog and business settings move to D1; the API computes prices (quotes)** (supersedes "catalog from shared seed data") | Admin edits must reach the website and the Android app without a deploy; price maths in one place instead of web + mock + Dart | — |
| 2026-11-16 | **Licence review is manual** (admin approves/rejects), with a `licenceAutoApprove` setting for unattended demos (supersedes the simulated review) | Rapido/Zoomcar pattern; an approval in admin is a strong demo moment | A KYC provider is chosen |
| 2026-11-16 | **Catalog in one `catalog_items` table (kind, id, JSON data)** with field definitions in `@quikfly/shared` (`catalog-kinds.ts`) driving API validation and admin forms | 12 kinds with simple shapes; one generic CRUD path instead of 12 tables, routes and forms | A kind needs relational queries (e.g. real bus inventory) |
| 2026-11-16 | **Seed copied in at first use** (one `json_each` insert), not a SQL seed migration | The seed is TypeScript shared with the demo; one statement stays under the free plan's 50 queries per request | — |
| 2026-11-16 | **Bookings are priced by quotes** (`POST /quotes` → `quoteId`, or the ride's fare via `rideId`); `amount` from clients is ignored; coupons are checked by the API and moved into L2 with this change | The website and the Android app can't change prices; one implementation of the maths (`pricing.ts`) shared by API and demo | A payment gateway is added (quote id becomes the order id) |
| 2026-11-16 | **Catalog and settings are cached 30 s per Worker isolate** | Saves a D1 read on every quote; admin edits show within 30 s everywhere (at once on the isolate that made them) | Edits must be instant everywhere (use KV or versioning) |
| 2026-11-16 | **Lean admin first** (login, roles, audit, dashboard, catalog + settings, bookings, licence queue, coupons); customers screen, booking notes, SOS handling, team screen and CSV export wait for Phase 5 | Owner's choice: get the website and app running fully on the API before the client demo, finish the back office after | After the client demo |
| 2026-11-17 | **First APK has full parity with the website** (all six services + account), built in slices M1–M6 | Owner's choice: the client demo shows the app doing everything the website does | — |
| 2026-11-17 | **App price estimates come from the API** (`POST /quotes` / `/rides/quote`, debounced), no Dart copy of `pricing.ts` | One implementation of the price maths; the app needs a connection anyway | Offline estimates are required |
| 2026-11-17 | **APK shared as a GitHub Release** on the public repo; the website's Play button links to it | Free, versioned, no login to download; keeps app updates out of website deploys | Play Store listing after sign-off |
| 2026-11-17 | **Android package id `com.quikfly.app`** | Neutral; can't change once on the Play Store | — |
| 2026-11-17 | **Flutter stack: Riverpod 3, go_router, Dio, flutter_secure_storage**; Dart models hand-written from `types.ts`, checked by a contract test against a live API | Common, well-supported packages; no code generation step; the contract test catches drift | Models grow enough to justify code generation |
| 2026-11-17 | **Web target kept in `apps/mobile` for development previews only** | No Android emulator on the dev machine; Chrome at 390 px gives fast UI checks of the same widgets | An emulator is installed |
| 2026-11-17 | **App signing password comes from an environment variable** (`QUIKFLY_KEYSTORE_PASSWORD`); `key.properties` holds only the key path and alias; a release build with a key but no password fails | The password never sits in a file or passes through an agent; a mis-set machine can't quietly ship a debug-signed APK that blocks future updates | Play App Signing after sign-off (Google holds the app key) |
| 2026-11-18 | **Cancellation policies are per-service settings** (`cancelPolicyBus/Tours/Rent/Group`, text tiers like `"15d:100, 7d:50"`), applied by the API inside the refund transaction; bookings copy `startsAt` from the quote and record `refundAmount`. Replaces the per-tour `cancellation` text and the hard-coded policy strings on four screens | The UI promised slabs while every cancel refunded 100% (competitor research, Phase 4b). One rule per service is easy for staff to reason about; text tiers fit the existing settings editor. Bookings made before keep a full refund (no start time) | Partners list their own inventory (then a policy per catalog item or operator) |
| 2026-11-18 | **Self-drive deposit is stored per booking and returned when staff mark the rental completed** (always in full on cancel, whatever the policy); customers can complete rides only | The deposit was charged inside the total but never returned on completion, and the rent policy could forfeit it on a late cancel. Staff completion stands in for "car returned and checked" until a rental lifecycle (odometer, photos, damage deductions) exists | The rental lifecycle is built (Phase 5) |
| 2026-11-18 | **Partner fleets: staff review every added vehicle and driver, renewals are checked, expiry blocks automatically**. Added vehicles go draft → submitted → approved (audit passed) → sticker → live; drivers need staff to tick police verification and induction training (and see the licence photo) before approval; one driver per vehicle; renewing a live vehicle's RC/insurance or a driver's licence keeps it running while staff check it; on the expiry date the cron blocks (`Expired: …`), lifted only when a checked renewal is valid. Partners can't edit live details beyond renewals | The 2025 aggregator guidelines require verified, trained drivers and valid vehicle papers; Red Taxi's vendor app shows the same document-expiry alerts. Server-side blocking means an expired vehicle can't be dispatched even if the partner ignores the warnings | Real trips are dispatched to partner vehicles (part 3), or a KYC vendor verifies licences/RCs automatically |
| 2026-11-18 | **QuikFly Partner is a second app in the same Flutter project** (flavor `partner`, `com.quikfly.partner`), modelled on Red Taxi's vendor app: a six-section application reviewed section by section, then onboarding (joining fee, agreement, sticker & paint). Partners use the customer phone login (a `vendors` row per user); document photos go to a private R2 bucket; the joining fee is simulated; vendor types are cars/autos and tempo travellers/buses/outstation | Owner asked for a dedicated vendor app like Red Taxi's and chose photos (will switch R2 on) and these vehicle types. One project shares the API client, theme and widgets, so fixes land in both apps; the customer flavor stays default so existing builds don't change. Real city rides through vendor cabs still need the state aggregator licence (research report), so this is the registration side first | Trips/earnings/payouts (next PRs), a payment gateway for the fee, or the aggregator licence |
| 2026-11-18 | **Services and features are switched in Settings (owner only)**: one switch per service (6) with a customer message, and switches for ride scheduling, extra stops, cash for rides, outstation/one-way, self-drive, trip offers and refer-and-earn. The API enforces them (409 with the message) and the apps hide what's off; existing bookings carry on. Things that already have a control (coupons: hide in catalog; credits, welcome credit, referral amount, surge: set to 0) get no second switch; SOS and trip sharing get none on purpose | Owner asked to control services and features from admin. Settings already give owner-only permission, audit, validation and a 30-second spread to web and app, so no new table or screen. Server-side enforcement means an old app version can't book a paused service. The 2025 aggregator guidelines require a panic button, so safety can't be turned off | Operations staff need to pause services themselves (move the switches to their own permission), or pausing per city is needed |
| 2026-11-18 | **QuikFly Credits are a separate ledger, not wallet money**: earned on completion (rides 5%, bus 2%, holidays/rentals/group 3% of what was paid, deposit excluded, up to ₹150 a booking), expire after 60 days, pay at most 50% of a booking, come back in the refund's share on cancel; all eight values are admin settings. Spending takes the soonest-expiring credits first inside the booking's `db.batch()`; balances are computed from unexpired rows, so expiry needs no job (the cron only records it) | Promotional credit that expires and can't be withdrawn must never look like wallet money (BluSmart left riders with stranded wallet balances); Uber One's 10% / ₹150 / 60-day shape is the market reference. Earning on completion means cancellations never need clawbacks; the 50% cap keeps every booking partly paid | A paid membership or a surge-waiving pass is added (Phase 5 #5, second half), or credits move to a points currency |
| 2026-11-18 | **Notifications are an inbox first, push second**: every event writes a `notifications` row (deduplicated by user/kind/ref) that web and app read; a one-minute cron adds ride reminders and pushes new rows through FCM HTTP v1 only when the `FCM_SERVICE_ACCOUNT` secret is set. Push is signed in the Worker (WebCrypto RS256), no Firebase SDK; the website polls the unread count every minute instead of web push | The inbox is useful today and testable without Firebase; FCM is free but needs the owner's Google project and a secret Claude must not handle. Sending from the cron (not inside the request) keeps bookings fast and inside the 50-query limit, and a failed push never fails a booking | Volume needs a queue (Cloudflare Queues), or customers want web push / email |
| 2026-11-18 | **Outstation cabs are group vehicles** (a sedan and an SUV beside the Innova, `trip: "oneway"` added to the group engine) rather than a new service; one way = max(distance, a day's minimum) × per-km × (1 + `groupOneWaySurchargePercent`) + one day's bata; multi-day round trips add `groupDriverNightAllowance` per night; vehicles that fit are listed smallest first | The group engine already had per-km with daily minimums, bata and destinations from Chennai (Savaari/Gozo pricing shape); a new ServiceKey would touch every map, policy and screen. New catalog rows reach production through migration 0012 (`INSERT OR IGNORE`) because the catalog was seeded long ago | Outstation becomes its own business line (own policy, GST treatment, entry tile) |
| 2026-11-18 | **Trips are a `trip_id` on bookings, started only from a booking's "Add a ride" offer** (no trips table, no automatic grouping); the trip summary lists each booking with its own tax invoice and a trip total, rather than one combined invoice | The useful part is the link and the timeline; services carry different GST rates and invoice numbers, so one merged tax invoice would be wrong. Boarding points map to ride places with a small table (`BOARDING_POINT_PLACES`, Chennai) because the bus timetable is generated | Real operator data with coordinates for boarding points, or trips the customer builds by hand |
| 2026-11-18 | **Multi-stop rides are priced by distance and time only**: the legs' distance plus `rideStopMinutes` (3) of waiting per stop at the option's per-minute rate; up to 2 stops (`RIDE_MAX_STOPS`) | No new kind of charge to explain; the fare stays "base + km + minutes" as the ride FAQ says. Uber's pattern (wait time at stops is billed as time) | Real GPS: then actual waiting is measured instead of assumed |
| 2026-11-18 | **Scheduled rides are started by the rider from My Trips** (from 15 min before pickup), not by a background job; the fare is locked at booking and priced at the pickup hour; cancelling is free until `rideScheduleFreeCancelMinutes` before pickup | No driver app or dispatcher: the rider's tap stands in for "driver assigned", which keeps the simulation honest and needs no cron. Uber Reserve pattern (book 30 min–90 days ahead, fare locked) | A driver app or dispatch exists (then assignment happens on the server near pickup) |
| 2026-11-18 | **Ride rules follow the Motor Vehicle Aggregator Guidelines 2025**: surge is capped by a `surgeCap` setting (default 2×) and every quote carries its `surge` for disclosure; riders give a reason from a fixed list when cancelling; without a valid (driver-side) reason and after `rideCancelFreeMinutes`, they pay `rideCancelFeePercent` of the fare up to `rideCancelFeeCap` (10% / ₹100). Wallet rides keep the fee from the refund; cash/UPI fees are recorded as owed and labelled "demo: not collected". Staff cancels never charge | Compliance shaped as settings, so a state's stricter numbers (e.g. Maharashtra's 1.5× draft) are an admin change. No driver app, so the driver-side penalty and police-verified driver rules wait | A driver app exists, or a payment gateway can collect owed fees |
| 2026-11-18 | **Bus seats booked through QuikFly are stored** (`bus_seat_holds`, one row per seat with the traveller's gender) over the generated seat map; the women-first rule (a free seat whose pair is held by a woman is women only) is applied by the API at quote time, for real and simulated bookings alike | Two customers could book the same seat, and the pink "ladies" seats were random and unenforced. MakeMyTrip/NueGo pattern; women are about a third of intercity travellers (redBus Pink Report 2026) | Operators supply real inventory (then holds come from their feed) |
| 2026-11-18 | **Roadside assistance is a setting, off by default**; off shows the support number for breakdowns | No RSA contract exists; the car page promised "24×7 roadside assistance" | An RSA partner is signed |
| 2026-11-18 | **Non-wallet refunds are shown as "Refund due"**, not "Refunded" | No payment gateway: nothing moves for UPI/card bookings, so the app records what is owed without claiming it was paid | A payment gateway is added |
| 2026-11-17 | **Keep the existing production data for the demo** (test accounts +91 90000 00001/00002, their bookings and licence, audit rows, rehearsal bookings); no cleanup, no catalog reset | Owner's choice: nothing irreversible before the demo; the data shows a working history | The client wants a clean slate (then a backed-up cleanup, Phase 4 option (b)) |
